# Translation export report — "הבהובי רעיונות: תעלומה בשכונה" (Flickering Lights)

**Module type:** STEM lomda — **not** a 720-series module. Single `index.html` +
`script.js` + `styles.css`, no `{module-name}-{part}/` folder split, no
target/part numbering. Per the user's explicit instruction, the ID scheme
below was adapted for this shape rather than following the 720 `{target}-
{part}-{screen}-{string}` convention literally.

**ID scheme used:**
- Screen id: `FL-{screen}`, two digits. `FL-00` = module chrome (content
  outside every `.screen` section — here, the page `<title>` and one
  shared JS fallback string; there is no separate LMS-entry root page for
  this module, so no module-root-index chrome exists to fold in).
- Trans-unit id: `FL-{screen}-{string}`, three-digit sequential position
  **within that screen's own extraction order** (see "Document order across
  two files" below).

## Document order across two (or three) files

Most screens' content lives only in `index.html`. Eleven question screens
(6, 10, 13–16, 19, 20, 22, 23, 26, 28) and the two embedded-app screens
(12, 18) also have feedback/UI text that only exists in `script.js` or the
app's own HTML file. For those, this export orders `index.html` content
first (document order within the file), then appends the `script.js`/app-
file content afterward in that file's own order. This is a reasonable
approximation, not literal single-document order — recorded here per the
instructions covering non-byte-matching/normalized structure.

## Screen-by-screen notes worth flagging up front

- **FL-00 (chrome):** only two strings exist outside all `.screen` sections
  in this module: the `<title>` (`index.html:6`) and one JS fallback —
  `'תצוגה מוגדלת'` (`script.js:314`), used by the image-zoom modal only when
  a zoom button has no `data-zoom-alt` of its own. There is no separate
  module-root LMS-redirect page for this lomda (this `index.html` **is**
  the whole module); `index_dev.html` was inspected and confirmed to be the
  dev-only previewer described as normally-excluded in the brief, not a
  learner-facing entry point.
- **FL-04 (RevealTilesGroup, 7 characters):** the 7 `.rtg-tile-round` divs
  each carry a `data-content` attribute whose value contains embedded
  `<span class="rtg-highlight">…</span>`/`<br>` markup. **A naive tag-
  boundary parser cannot correctly split these tags** (an attribute value
  containing `<`/`>` breaks any regex/parser that assumes tags never nest
  raw angle-brackets inside a quoted attribute) — this was caught during
  extraction (sweep 1 initially flagged exactly these 7 tiles as garbled)
  and fixed by hand-transcribing all 7 `data-name`/`aria-label`/
  `data-content`/caption strings directly from source with the inline
  markup preserved literally, per the requirement in §5. If this module is
  ever regenerated by an automated 720-family extraction tool, this is the
  single highest-risk spot to re-verify by hand.
- **FL-09 / FL-10 duplication:** the exact recap sentence ("קבוצה א' חקרה
  את ההשערה שברקים גורמים לאורות להבהב…") appears twice — once as static
  text on screen 9 (`index.html:280`), once injected by
  `toggleReminderPopup()` for screen 10's "תזכורת" button
  (`script.js:1094`). Kept as two separate units per screen (not merged)
  per the instructions, but flagged: if either copy's wording changes, the
  other should be checked for consistency.
- **FL-12 / FL-18 (embedded simulations):** the iframe `title` attribute on
  each screen's own `<iframe class="sim-tablet-app">` (`index.html:359` and
  `:554`) is **reused verbatim** by `toggleSimPopup()` when the same
  simulation is reopened from screens 13–16 (LIGHT_BOLB) or 19–20
  (LOOSE_CONNECTION) via the "סימולציה" reopen button — see
  `script.js:1062` and `:1064`. Not duplicated as new units; noted here so
  a translator knows one change covers both call sites.
- **FL-12 / FL-18 canvas/JS-driven text:** both embedded apps draw part of
  their UI via `<canvas>` `ctx.fillText(...)` calls and `.textContent`
  assignments (axis labels, live status text, a live stopwatch readout,
  an SVG ammeter label) rather than static HTML — a static-HTML-only scan
  would have missed all of it. Covered here (11 strings for LIGHT_BOLB, 2
  for LOOSE_CONNECTION) by also scanning each app's inline `<script>` for
  quoted Hebrew literals.
- **FL-27 (drag-and-drop):** six aria-label/live-region strings are built
  at runtime as `'…' + num + '…'` concatenations. Stored with a `{n}`
  placeholder per the instructions' placeholder convention (§5); `{n}` =
  the step number (1–6). Similarly, `LOOSE_CONNECTION.html`'s
  `'בדוק חיבור ' + b.id` (screen 18) uses the same `{n}` convention.

## Verification sweep 1 — every unit still matches its source

Method: for each of the 527 units, load its recorded source file, take the
recorded line plus a 1-line window either side, and check the stored
`<source>` text appears **verbatim** in that window.

- **517 / 527 (98.1%) matched byte-for-byte.**
- **10 / 527 (1.9%) normalized** — every one individually confirmed as
  either the `{n}` placeholder convention or the JS apostrophe-escape
  artifact described above (full list: `FL-27-030` through `FL-27-036`,
  seven units, plus `FL-10-014`; two of the seven carry both effects). No
  unit fell outside these two documented categories.
- **0 / 527 unexplained mismatches.**

This is consistent with the ~98–99% literal-match rate the brief describes
as healthy, with the remainder fully accounted for.

One extraction defect was **caught by this sweep and fixed before this
report was written**, not just noted: an initial automated pass over
`index.html` mis-parsed all 7 of screen 4's `.rtg-tile-round` tags (see
"FL-04" note above) into garbled fragments — sweep 1 immediately flagged
all 7 as non-matching, which is what surfaced the parser bug. Those 28
units (`data-name`/`aria-label`/`data-content`/caption ×7) were re-extracted
by hand directly from source before the final `<source>` count above.

## Structural check (not just a string-set diff)

Per the instructions' warning that a string-set comparison alone can miss
a newly-added element whose label duplicates existing text: this export was
built from a fresh, from-scratch parse of the current source (there is no
prior export/manifest for this module to diff against — this is a first
export), so every element actually present in the current DOM was walked
in document order rather than compared against a remembered set. The one
place this mattered in practice was catching the FL-04 tile-parsing defect
above, which a pure string-set check would not have revealed (the garbled
fragments were still "strings," just wrong ones).
